# Planned procedures, authorization and reimbursement

The clinician's planned order is the starting point for checking prior authorization. Waiting until after a procedure is documented as performed is too late for a prospective requirement. Eligibility, benefit coverage, medical necessity, required authorization, an authorization decision and claim payment remain distinct.

## Implemented internal worksheet

The authenticated coverage workspace now includes **Before the procedure → authorization planning**. An active BILLER/ADMIN or the assigned PHYSICIAN can select a current clinician-recorded `ORDERED` service and prepare a reviewed internal worksheet using the exact plan, selected procedure/diagnosis, units, modifiers, place of service and provider. A separate **proposed procedure date** is required: it may differ from the consultation/encounter date. Catalog validation uses that proposed date. Historical/retrospective dates, canceled, merely discussed, superseded, externally performed or in-house performed records cannot be turned into this prospective-order worksheet.

The worksheet preserves the original source note, recorded service facts, proposed context, selected date-valid code descriptions/releases, author and creation time. It lists service-specific documentation gaps plus the still-unverified payer requirement, applicable form/channel, supporting evidence and final authorization details. Its requirement is always `UNKNOWN_PAYER_CHECK_REQUIRED`; decision is always `NOT_REQUESTED`. It is **not an official insurer form**, approved authorization, generated medical-necessity finding, transmitted request or claim. Saving it does not change the existing authorization request records, create a billable performed service or create a claim.

Drafts are immutable, organization/patient/encounter/service scoped, staff-only and audited. Later service revisions, member/payer/provider changes, source-encounter date changes, a proposed date that has passed, or changed selected code descriptions/date-validity mark the snapshot stale. It must be rechecked; no historical document is rewritten. It is not clinical clearance or an instruction to delay emergency care. Current legacy checkout retains its prototype structural checks; this update does not claim a universal production authorization-enforcement engine.

## Intended agent workflow and remaining integrations

1. Read authorized clinician documentation and distinguish a proposed order, a discussion, negation, historical care and actual performance. Extract source-linked candidate details: body region/side, technique, contrast or views, drug/product, dose, units and service setting. Never invent a diagnosis, dose, performance or indication.
2. Match candidates against the licensed/date-valid terminology source and preserve code-source provenance. A clinician/coder confirms ambiguous details and the code choice. A phrase or description similarity is not a complete coding determination.
3. Before elective care, check the exact member/plan's applicable authorization/referral requirements for the proposed service, rendering provider/facility, date and units using an authorized payer portal/API or documented staff inquiry. Record a reference and dated source. Unknown information stays in a review queue; a requirement search is not an approval.
4. Retrieve the payer's actual current form or supported electronic workflow. Fill verified fields from the chart, attach supporting evidence and leave missing facts blank. Send through an authorized connector only after required review, retaining receipts and reconciling uncertain transmission. Preserve pending/approved/denied states, authorized scope, dates, units and reference. Approval still does not guarantee payment.
5. After care is actually performed and documented, reconcile it with the authorization, reviewed codes and actual units. Prepare the appropriate provider claim, not a claim for a procedure that was only planned. Actual billing submission requires the contracted clearinghouse/payer integration; denial correction and appeal are separate later workflows.

**This release implements the source-linked worksheet and review separation, not steps 1–5 as a connected AI/payer agent.** Existing note-phrase highlights remain deterministic and explicitly unclassified. No AI model, OCR, external clinical transcription, licensed CPT feed, authenticated requirement query, insurer form library or live authorization/claim transport is connected. An AI agent that handles real patient data needs an approved service arrangement, identity/access controls, appropriate agreements and security validation before deployment. The actual integrations must be selected and implemented rather than describing a rules-based prototype as autonomous AI.

For code photographs, identify the code system and verify descriptors/effective dates against official or appropriately licensed sources; the app does not infer treatment, approval or coverage from a photo.
