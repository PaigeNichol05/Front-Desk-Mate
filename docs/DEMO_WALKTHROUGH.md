# Demo walkthrough · fictional records only

Use Node.js 24+ and run `npm run demo:complete` from the project root, then open the printed local URL. This starts the authenticated SQLite application and enables synthetic audio and the test-only clearinghouse for the bundled fictional patient. Ordinary `npm start` requires the [README environment setup](../README.md#environment) and defaults simulation off. `npm run demo:host` is a separate browser-only concept with no login, database or official catalog. Neither mode connects to an insurer or is ready for real patient use.

## Authenticated appointment-to-claim walkthrough

1. Sign in as `doctor@example.test` with `DemoOnly!ChangeMe123`. Open **Patients → Jordan Sample → Open** to view the seeded encounter. Start with an open encounter: signed/checked-out records and other local demo state persist across restarts. Use a separate fresh project copy for independent scenarios. Try the optional audio flow below before signing.
2. Add fictional **ASSESSMENT**, **PLAN** and supporting service documentation. Other structured sections include symptoms, medications, exam, lab, consent, calls and dictation text. Files accepts synthetic PNG/JPEG/PDF uploads. There is no live transcription or automatic clinical interpretation.
3. Before signing, use **What happened at this appointment?** to select a supporting note and record what occurred. Distinguish discussed, ordered/referred, performed here, performed elsewhere and canceled. Complete the relevant indication, site/laterality, imaging protocol/views, medication formulation/dose/route, technique and performed-service reference. Exact-phrase highlights are clarification prompts, not proof of care or billable services. See [appointment coding](APPOINTMENT_CODING.md); its [automated fixture](../test/appointment-coding.test.js) provides a synthetic medication example for software testing, not a clinical recommendation.
4. Open **Billing codes & insurance coverage** inside the encounter to search official dated CMS descriptions, as described below. If the service needs CPT, an authorized administrator must first supply appropriately licensed data; no CPT catalog or ADMIN account is seeded. Missing catalogs or service details stay unresolved rather than producing invented candidates.
5. Click **Sign encounter**. In the source-linked workspace, the assigned physician or biller/admin can then review a date-valid procedure and documented diagnosis, modifier, units and rationale. Only sufficiently documented in-house performed services can receive a performed-service code review. This is human review backed by catalog/source evidence, not proof of coding correctness, clinical necessity or coverage.
6. As the assigned physician, select the reviewed lines, enter charges and any applicable approved authorization reference, then click **Create claim from selected reviewed services**. This supports multiple lines and retains immutable source-review links. Checkout checks signed assessment/plan, payer/member identifiers, structural validity, source matches and any supplied authorization reference; it does not verify eligibility or all payer requirements. The older **Checkout & billing** manual path remains only for legacy encounters without service records. Its test CPT values are specimens, not licensed catalog validation; toxin drug codes still require detailed source-linked records.
7. Sign out, then sign in as `biller@example.test` with the same password. In **Billing**, open the claim. Checkout atomically created a queued event and persistent outbox snapshot; the underlying claim is `AWAITING_CONNECTOR` because no real submission occurred. In **Test clearinghouse transmission**, choose one fictional outcome and click **Queue fictional simulation**. The worker processes it every second; **Process due fictional transmission** requests an immediate due attempt.
8. Inspect separately labeled fictional transport acknowledgment, clearinghouse acceptance/rejection, payer acceptance, adjudication and denial/remittance events. The staff display uses `SIMULATED_*` projections, with revision, attempt count and submission identifier. A completed fictional rejection allows reviewed changed lines and a correction reason to create a new revision; an adjudicated denial requires staff review and has no automatic resubmission. The correction form currently handles legacy manual lines; it does not preserve source-linked/toxin metadata. For those claims, use the correction API with matching reviewed provenance; see [clearinghouse foundation](CLEARINGHOUSE_FOUNDATION.md). Each queued revision has one fixed scenario. No simulated remittance creates a patient payment entry or changes the underlying claim status.
9. Sign in as `patient@example.test`. The patient sees Jordan's authorized records/files, appointments and local authorization information. Claim lists show generic `PRACTICE_PROCESSING`, omit member IDs and exclude internal denial/transmission history. The patient cannot sign encounters or access staff coding/coverage endpoints. Billers can separately create local authorization requests, manually record denials/payments through the API and draft appeals; none is an insurer response or external submission.

### Official code lookup and coverage evidence

As biller, open **Billing → Billing codes & insurance coverage**; the clinician has the same lookup within an encounter. Search by code or description and service date. The bundled CMS releases contain 7,448 non-dental HCPCS Level II entries for October–December 2026 and 74,879 billable FY2027 ICD-10-CM entries for October 1, 2026–September 30, 2027. Results show descriptions, effective dates and the official source. Dates outside installed releases report unavailable. CPT descriptions require private licensed import by an active organization ADMIN; the importer records attestation and provenance but does not grant or verify licensing rights. See [CODES_AND_COVERAGE.md](CODES_AND_COVERAGE.md).

To exercise the evidence workflow, select Jordan's encounter, an exact fictional plan/product reference, procedure, documented diagnosis, modifier, units and place of service, then **View coverage and code alignment**. It begins **Coverage not verified**. As biller, expand **Record a staff review of benefit evidence**, fill every required evidence field using fictional source references and valid review/recheck dates, and save the immutable review. Use a current checked date and an expiry/recheck date on or after today to view current evidence; past-dated examples expire.

A plan-document review displays **Plan policy only · member coverage not verified** and cannot establish a covered member benefit. Portal/call entries are staff assertions, with `authenticated_insurer_response:false`; the app never logs into an insurer. Exact patient/member/payer/plan/provider/date/code/diagnosis/modifier/unit/setting context must match; changes return unverified, and expired evidence cannot project current coverage. Benefits and authorization never guarantee payment. This evidence panel is separate from checkout validation, not an automated eligibility or payer-rule gate.

### Detailed medication and toxin records

For a fictional administration, the assigned clinician selects **Medication administration** or **Botulinum toxin / Botox-type treatment** before signing and links the supporting note. General medication fields include formulation, dose, route and performance reference. The toxin editor additionally records actual product, each vial and injection site, history/necessity/consent/guidance, and explicit administered/discarded/remaining/other-use units. It reconciles totals and uses the product's own HCPCS denominator; no potency conversion or dosing advice is provided. After signing, administered and discarded drug components receive separate reviews with an explicit payer-wastage source. Limited JW/JZ checks apply only to the reviewed setting; fractional rounding and unsupported allocations stay held. See [BOTULINUM_ADMINISTRATION.md](BOTULINUM_ADMINISTRATION.md) for scope and gaps.

For a hosted fictional-data demonstration, isolate the environment, keep it separate from eventual production, restrict access, and avoid using any real identifiers or documents. There is no production user onboarding in this starter.

## Durable synthetic audio walkthrough

Before signing or checking out the seeded encounter, opt in with `FICTIONAL_AUDIO_DEMO=true`, `SEED_DEMO=true`, and `NODE_ENV=development`; keep the database and `AUDIO_DIR` on private persistent storage. Sign in as physician, open the encounter and create a fictional attempt. Agree as the physician, then sign in as patient and agree separately. Return to the physician encounter, refresh consent status, start and finish the synthetic attempt. Replay the generated tone, approve review, and release to the portal. The patient can replay/download it in **Files** or the encounter view, or withdraw consent to remove access and erase the file. Stop an unfinished attempt to discard it. No microphone is used, no real audio can be uploaded, and no speech service is connected. See [API.md](API.md) for authorization, expiry, audit and deletion rules. The Railway concept demo remains separate and keeps its synthetic sample only in browser memory.

## Denial correction concept

Run `npm run demo:host` and open `/billing-demo` on that concept server. As Billing staff select **Search Jordan’s sample chart**, then **Request missing documentation**. Switch to Assigned physician and **Load reviewed fictional addendum**. Switch back to Billing staff, **Prepare sample packet**, and **Mark packet reviewed**. Deselect the addendum to see the evidence hold; change provider to reset packet review; switch to Patient to see the limited status view. All policies and data are fixed fictional fixtures, not live insurer requirements. **Simulate corrected resubmission** produces a browser-only sample receipt; it does not use the authenticated outbox or send a claim. No official catalog or payer form is connected, and browser role switches are not authentication. Reload resets this concept flow.

## Visit order in the concept preview

Select Physician or Medical assistant and open Patients. Record check-in, then taken back/rooming. The physician records provider assessment, assessment documentation, and the visit care plan, then signs and checks out after billing review. Care-plan completion and reviewed visit-draft saving are disabled before the provider-seen milestone; an MA cannot complete or sign the clinical plan. Pre-visit preparation is separate from documenting completed care. These browser milestones are simulated; the authenticated API does not yet persist or enforce this arrival workflow, and role switching is not authentication.

## Visible denial form and clinician contact

The concept navigation now includes **Denials & resubmissions**, embedding the fixed Jordan Sample case with a visible denial record and prefilled reconsideration-form preview before chart search. The preview is not an official payer form and cannot transmit. Simulated claim denials appear in the staff view of the selected chart’s Documents screen until reset; they are hidden in the patient view. In Messages/Inbox, enter fictional text in **Write a question for the doctor**; the physician can acknowledge the request in Inbox. No live AI, messaging, or server persistence is provided for these concept controls.

The clinician draft includes reason, findings, assessment, services/actions, plan, follow-up, and optional relevant history/prior treatment, procedure detail, and actual time fields. The core draft checklist checks presence only. It does not establish billing-code support or insurer acceptance. Final draft saving requires the provider-seen milestone and the sample core fields. Real code/service/payer requirements need a licensed, verified integration.

## Portal landing page

The preview opens on Today, with Doctor portal and Patient portal labels selected by the role control. Documents holds the chart files and any simulated denial history. Denials & resubmissions is a staff navigation item rather than the first page; patients see only their sample claim status and own document cards, not the staff correction form.

## Assessment-to-plan draft concept

After check-in, rooming, and provider assessment, load the fixed fictional dictation example. **Generate fictional care-plan draft** creates an unsigned fixed specimen linked to that sample assessment; **Review and copy draft to plan field** copies it for editing. A changed assessment invalidates the generated draft. Neither action signs the encounter or records the completed clinical plan milestone. The sample plan leaves management details and timing for clinician completion. Arbitrary assessments are unsupported; no real transcript, microphone, transcription, AI model, or treatment inference is connected.

Production requirement: with documented participant consent and an approved protected recording/transcription/AI arrangement, retain the assessment source/version, generate an evidence-linked draft with missing details flagged, and require the qualified rendering clinician to review, edit, and approve it before publication/signing. Never invent findings, care performed, medications, or unsupported clinical decisions. Provider/plan changes invalidate relevant review.

## Multiple activities and internal resubmission

In Patients, select any combination of **Review care plan**, **Update care plan**, **Discuss injection**, **Review medication**, and **Review imaging**. Each toggles independently and does not assert that a procedure occurred or assign codes. A primary appointment type still determines calendar availability.

Patients do not see internal denial records, reason text, correction forms, or denial/event history. Staff open **Denials & resubmissions**. The fixed form fills from sample claim fields; after physician evidence is added, returning to Billing staff automatically prepares the sample packet. Mark it reviewed, then **Simulate corrected resubmission** to see a clearly labeled sample receipt. There is no insurer transmission, verified official payer form, or real automatic retry. Production automation must follow verified correction/appeal rules, authorized review, original-claim references, and idempotent delivery.
