# Appointment-driven coding review

The clinician’s documentation drives the workflow. Clinical decisions about which tests or treatments are needed remain with the clinician. Coding suggestions do not prescribe a service, add a diagnosis, establish medical necessity or imply coverage.

## Use the appointment workspace

1. Write the appointment assessment, plan and supporting service documentation.
2. Open **What happened at this appointment?** The app highlights limited exact phrase mentions (CT, X-ray, MRI, ultrasound, lab terms, injection, therapy and selected procedures) from notes. Each mention preserves its source ID, excerpt and exact offsets. These are unclassified mentions: a phrase can be historical, negated or canceled. **Clarify this mention** starts a form; it does not create an order or code.
3. The assigned clinician confirms the actual service facts while the encounter is open. Pick a source note, service category, status and exact description. Multiple separate services can be recorded. Status distinguishes discussed, ordered/referred, performed here, performed elsewhere and canceled. This is an internal record, not an electronic referral/order transmission.
4. Complete relevant details: indication; imaging/procedure region and laterality or explicitly documented not-applicable; CT/MRI contrast protocol; X-ray view count; drug/formulation, administered dose and route; specific service/technique; performed-service report or administration reference. Missing fields stay visible as clarification requests. These are a baseline checklist, not every specialty’s coding requirements.
5. Catalog search terms from the documented service produce description matches using the installed date-valid HCPCS catalog or the organization’s licensed CPT import. These are candidates for professional review, not semantic matches proven against technique, units or diagnosis. No candidate is invented when a catalog is unavailable. Imaging/visit/procedure descriptions generally require the licensed CPT catalog, which is not supplied.
6. Sign the clinical record. Assigned clinician or billing staff can then select and attest to a source-linked procedure code, diagnosis, modifier and billing units with a rationale. The review validates catalog presence and service date. It does not automatically derive a diagnosis from symptoms, prove clinical indication, calculate drug units, validate bundling/NCCI or apply payer-specific rules.
7. Select reviewed performed-service lines and charges to create one local claim containing multiple lines. Each line links to the immutable review and original service/source note. Planned, discussed, canceled and externally performed services cannot be reviewed as this clinic’s performed-service billing. Patient benefits, provider enrollment and payer requirements remain separate checks; real payer transmission is disabled.

Service revisions append history before signing; the current version supersedes the prior record. Signed service facts are locked. A real signed-record amendment process is not implemented. Billing code reviews can append after signing/check-out for corrections, without changing the clinical facts. Duplicate source IDs and duplicate service/procedure/modifier combinations in a claim are rejected. Two genuinely separate documented services require separate service records.

When an encounter has service records, each checkout line must have a matching current code-review source. Tampered code/diagnosis/units/modifiers and cross-encounter/organization references are rejected. Legacy demo encounters without service records retain manual checkout so existing demonstrations are compatible; this is an explicitly limited migration path, not a production billing-validation guarantee. Clinical coding rules and safe production enforcement still require professional review.

## Persistence and access

`encounter_services`, `service_code_reviews` and `claim_line_sources` preserve immutable service revisions, review evidence and claim-line provenance. The outbox snapshot also retains source review IDs. Active same-organization BILLER/ADMIN/PHYSICIAN users can read the internal workflow. Only the assigned physician can record/revise service facts while open. Billing staff or the assigned physician can review signed service codes. Patients cannot access these staff endpoints. Session/CSRF protect writes and audit events record reads, service creation/revision and code review.

Endpoints: `GET/POST /api/encounters/:id/services`; `POST /api/encounters/:id/coding-review`. Service writes include `source_section_id`, `category`, `state`, `description`, relevant detail fields and `reviewed:true`; optional `supersedes_id` creates a new current revision. Code review requires `service_id`, `procedure_system`, `procedure_code`, `diagnosis_code`, `modifier`, `units`, `rationale`, `reviewed:true` and an installed date-valid catalog. Returned line includes `source_review_id` for checkout. No service record or code is auto-created by phrase detection.

## Remaining work for automatic coding

No live audio transcription, AI clinical extraction, validated descriptor-to-service mapping, specialty coding engine, licensed CPT release, payer-rule engine, order-routing integration or automatic eligibility transport is introduced. The new workflow supplies the source trail and review gates needed for those integrations. Do not claim it automatically assigns the correct imaging or procedure code. Professional validation must cover actual body region/protocol/views, drug dosage units, professional/technical components, bundling, service location, rendering provider, medical necessity and applicable payer requirements.

Detailed botulinum-toxin treatment adds individual vial/site traceability, product-specific units, reconciled disposal/allocation and explicit payer-wastage review. See [BOTULINUM_ADMINISTRATION.md](BOTULINUM_ADMINISTRATION.md). No product-specific dose is recommended and no potency units are converted between brands.
